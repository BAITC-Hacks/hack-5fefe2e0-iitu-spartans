# Журнал итераций LLM-роутера

Dev-набор: `case_2/voice_router_dataset/dev_utterances.json` (104 реплики), пустой state, `scripts/route_batch.py` (concurrency 8).
Латентность — время одного вызова `responses.parse` на стороне клиента (сеть + модель), статичный префикс кэшируется (`prompt_cache_key`).
Каталог в промпте: ~5,2 тыс. токенов (сценарии: id, name, domain, priority, description, not_this_if, 2 ru + 2 kk примера из `examples`; системные интенты) + ~0,8 тыс. (форматы слотов); весь вход ≈ 8,3 тыс. токенов, из них ~94 % кэшируется.
Промпт улучшается только инструкциями и правилами различения из `scenarios.json`; тексты dev-набора в промпт не попадают.

## v0: первый рабочий прогон
Ошибки (3 по primary, 2 по full_match):
- U100 «Какая погода завтра в Алматы?» → модель вернула **пустой** `scenarios` (router подставил SYS_UNCLEAR). Промпт не говорит явно, что системный интент тоже кладётся в `scenarios`.
- U084 «каско и обязательную» → SC01, SC03: набор верный, но нарушен порядок упоминания.
- U030 «Шетелде аяғымды сындырып алдым, сақтандыруым бар» → SC16 вместо SC15: модель решила, что раз помощь «не срочная», это выплата по НС.
- Язык (не входит в evaluate): U042 kk определён как ru.

## v1: системные интенты, срочность за границей, признаки казахского
Изменения в инструкциях: `scenarios` никогда не пуст, системные интенты кладутся туда же; «за границей + болен/травма → SC15 независимо от формулировки, SC16 — только выплата по полису НС»; признаки казахского (буквы ә ғ қ ң ө ұ ү һ і, казахские окончания); сортировка по позиции в тексте.
Результат: primary 0.971 → 0.971, full_match 0.981 → 0.981, язык 101 → 103/104, медиана 1736 → 1708 мс.
- Исправлено: U100 (off-topic → SYS_OUT_OF_SCOPE), U042 (язык).
- Не исправлено: U030 (SC16 вместо SC15), U084 (порядок: модель ставит SC01 раньше SC03, т.е. в порядке каталога).
- Новая ошибка: U012 «страховка для шенгенской визы» → SC39.
Вывод: модель выбирает ID до того, как разобрала реплику. Инструкции без изменения схемы вывода не помогают.

## v2: разбор до выбора (situation + quote)
Изменения: в схему вывода добавлены поля, которые модель генерирует до ID. `situation` (≤ 15 слов: когда событие, где клиент, роль, есть ли полис) и `quote` в каждом сценарии (точный фрагмент реплики); сценарии идут так, чтобы quote шли слева направо. Правило SC39/SC06 уточнено: нужна сама страховка (даже для визы) → SC06, документ по уже существующему полису → SC39.
Результат: **primary 0.971 → 1.000**, full_match 0.981 → 0.990, медиана 1708 → **1946 мс** (+~25 выходных токенов), p90 2710.
- Исправлено: U030, U084, U012.
- Осталось: U019 «застраховать 120 сотрудников, куда обратиться?» → SC10 + лишний SC33 (вопрос «куда» понят как запрос адреса офиса).
- Язык: 99/104. Все 5 расхождений — mixed, помеченные как kk (сигналы казахского перетягивают); `response_language` = kk, что соответствует правилу по D04.

Дополнительно по gpt-5.4-mini:
- concurrency 1 (без параллельной нагрузки): медиана 1612, p90 2328. Параллельность замер не искажает.
- `service_tier=priority`: медиана 1542, p90 2255, выигрыш ~5 %. Оставлено опцией `ROUTER_SERVICE_TIER`, по умолчанию выключено.
- Разложение задержки (линейная регрессия по 104 вызовам): ≈ 1050 мс фиксированно + ~6 мс на выходной токен. RTT до api.openai.com ~115 мс, TLS ~180 мс, пустой запрос ~0,4 с. Сокращение вывода со 112 до ~95 токенов (v3) почти не сдвинуло медиану: основное — время до первого токена.
- **Вывод:** удалённый вызов роутера даёт ~1,5 с медианы, что не укладывается в «паузу ≤ 1 с» из постановки. Это нужно закрывать на уровне конвейера (параллельный старт, стриминг, ранний разбор scenario_id из потока, короткая фраза-подтверждение), а не только промптом.

## v3: модель по умолчанию и короче вывод
Изменения: модель по умолчанию gpt-5.4-mini (reasoning `none`); `reason` ≤ 8 слов, `situation` ≤ 10; альтернативы только при уверенности < 0.9 (было непустых 34 из 104, стало 3); SC33 — только адрес/часы офиса, «как/где получить услугу» относится к основному запросу; mixed = есть и русская, и казахская клауза.
Результат (2 прогона): primary 1.000 / 1.000; full_match 0.981 / 1.000; медиана 1648 / 1580 мс; выходных токенов 112 → 94,5.
- U019 (лишний SC33) исправлен.
- В первом прогоне U013 получил лишний `SYS_UNCLEAR` с confidence 0.2 («context only, not separate request»), U035 — лишний SC14. Во втором прогоне этих ошибок нет, т.е. это шум (у gpt-5 нельзя задать temperature).

## v4: согласованность вывода
- v4a: правило «в `scenarios` только уверенные (≥ 0.5), подозрения — в `alternatives`» + «SYS_* не смешивается с SC». Регресс: U084 в обоих прогонах склеивал «каско и обязательную» в один SC03, а SC01 уходил в alternatives (0.55/0.63). Правило про alternatives откачено.
- v4 (итог): оставлено «SYS_* никогда не идёт вместе с бизнес-сценарием» в промпте и тот же инвариант в коде (`router.py` выбрасывает SYS_* при наличии SC); из `not_this_if` SC03 («про ОГПО → SC01») добавлено: оба продукта в одной просьбе = два запроса SC03 и SC01 в порядке упоминания.
- Результат (2 прогона): primary 1.000 / 1.000; full_match 0.981 / 1.000; медиана 1476 / 1585 мс, p90 2012 / 2277.
- Нестабильные реплики (ошибаются не в каждом прогоне):
  - U035 «Какие бумаги нужны, если затопили квартиру?» → SC18 + лишний SC14. Модель считает упоминание залива отдельным заявлением об убытке. Пограничный случай: придаточное «если затопили» — условие, а не сообщение о событии.
  - U083 «…КАСКО бар, и ещё подскажите, где у вас осмотр делают» → SC13 + SC33 вместо SC20. «Где делают осмотр» модель иногда читает как адрес офиса, хотя в `not_this_if` SC33 прямо сказано «где осматривают авто по убытку → SC20». Контекст «убытка ещё нет» (SC20 требует заведённого убытка) тянет модель от SC20.
