# Архитектура Voice Router: решения и их история

[README](README.md) · [Правила работы](AGENTS.md) · [Навыки для агентов](.agents/skills/)

Документ фиксирует архитектурные решения в порядке их принятия: контекст, решение, последствия и где решение
реализовано. Схемы (конвейер, ход диалога, политика, модель, схема БД) — в [README, раздел 2](README.md#2-архитектура).
Новое решение добавляется в конец журнала; прежние не переписываются — изменившееся решение получает новую запись
с отметкой, какое оно заменяет.

## Журнал решений

### ADR-001. Модульный монолит на Next.js и TypeScript

- **Статус:** принято, реализовано в #14 и #16.
- **Контекст:** 5 часов, 3 участника, проверка жюри запуском по README (Положение §5.4.16). Каждый лишний сервис —
  ещё одна точка отказа при запуске у проверяющего.
- **Решение:** одно приложение Next.js 16 (интерфейс и маршруты API) и пакет `@voice-router/core` с модулями, у которых
  явные границы и контракты. Рабочее пространство pnpm.
- **Последствия:** запуск одной командой; модули проверяются независимо; отдельный сервис подключается без изменения ядра.

### ADR-002. Сценарий выбирает LLM, а не классификатор намерений

- **Статус:** принято, реализовано в #21.
- **Контекст:** ТЗ, Must-have: «Intent-классификатор энкодерного типа не засчитывается». Классификатор ломается на
  смене темы, запросах на стыке сценариев и смешанной речи.
- **Решение:** модель получает описание каждого сценария и правила разграничения `not_this_if` из данных набора и
  выбирает по смыслу и контексту диалога; несколько намерений — в порядке упоминания.
- **Последствия:** качество зависит от описаний каталога, а не от обучающих фраз; новые сценарии добавляются данными.
  Промпт детерминирован, неизменный каталог в начале — префикс кэшируется моделью, задержка ниже.

### ADR-003. Ответ модели — недоверенный ввод

- **Статус:** принято, реализовано в #14 и #21.
- **Контекст:** модель может вернуть текст вместо JSON, нарушить формат или назвать несуществующий сценарий.
- **Решение:** контракт `RouteDecision` (Zod) и проверка, что каждый сценарий есть в каталоге; один повтор; затем отказ
  с причиной без исключений. Модель подставляется функцией — тесты работают без сети и ключей.
- **Последствия:** в политику и трассировку попадают только проверенные данные; сбой модели превращается в уточнение.

### ADR-004. Политика решений детерминирована и отделена от модели

- **Статус:** принято, реализовано в #15.
- **Контекст:** README набора задаёт пороги: не ниже 0.75 — запуск, 0.45–0.75 — уточнение, ниже 0.45 дважды или по
  просьбе клиента — оператор; срочные сценарии первыми.
- **Решение:** модуль `policy` без вызова модели; пороги — именованные константы, их же использует интерфейс для цвета.
- **Последствия:** поведение предсказуемо и покрыто тестами; пороги меняются в одном месте.

### ADR-005. PostgreSQL и нумерованные SQL-миграции

- **Статус:** принято, реализовано в #16.
- **Решение:** файлы `db/migrations/NNN_описание.sql`, каждый один раз в своей транзакции; advisory-блокировка;
  слитая миграция не редактируется.
- **Последствия:** схема одинаково собирается на чистой базе у проверяющего; миграции применяются при старте.

### ADR-006. Точные версии и запуск одной командой

- **Статус:** принято, реализовано в #14 и #16.
- **Решение:** версии закреплены точно, установка по lock-файлу; Docker Compose поднимает базу и приложение; слои
  образа упорядочены для кэша — изменение кода не пересобирает зависимости.
- **Последствия:** у проверяющего устанавливается ровно проверенное командой.

### ADR-007. Проверка без облачного CI

- **Статус:** принято, реализовано в #14.
- **Контекст:** задачи GitHub Actions в организации хакатона не стартуют из-за блокировки биллинга организации.
- **Решение:** workflow с ручным запуском; та же цепочка локально — `pnpm verify`.
- **Последствия:** нет ложных провалов на pull request; автозапуск возвращается одной строкой.

### ADR-008. Разработка через тесты и GitHub Flow

- **Статус:** принято, действует с #13.
- **Решение:** модуль начинается с падающего теста (отдельный коммит), затем реализация; ветка на задачу, pull request
  с ревью, слияние merge commit без squash.
- **Последствия:** в истории видно, какое требование проверено и кем; авторство сохраняется.

### ADR-009. Голос: сначала браузер, затем поток голосовой модели

- **Статус:** браузерный голос реализован в #27; поток голосовой модели — развитие.
- **Контекст:** ТЗ: голос в вебе, ориентир 1,5 с от конца речи до ответа, возможность перебить робота.
- **Решение:** распознавание и синтез речи средствами браузера (ru-RU, kk-KZ) с замером `sttMs` — работает без ключей;
  поток по WebSocket к голосовой модели подключается следующим шагом без изменения API хода.
- **Последствия:** голосовой сценарий доступен сразу; задержка распознавания показывается в панели отдельным этапом.

### ADR-010. Сервис выбора сценария на FastAPI и резервный путь в ядре

- **Статус:** принято; ядро — #21, #24; сервис — #23.
- **Контекст:** параллельно в команде выполнен маршрутизатор на Python/FastAPI с замером на dev-наборе
  (primary 1.000, журнал итераций в ветке сервиса). Два решения одной задачи требуют явного разделения ролей.
- **Решение:** основное приложение — Next.js; сервис FastAPI — источник решения при заданном `ROUTER_URL`
  (эндпоинт `POST /route`, ответ по контракту `RouteDecision`, проверяется тем же Zod-контрактом). Без сервиса решение
  принимает маршрутизатор ядра с моделью (`OPENAI_API_KEY`), без ключа — демо-режим.
- **Последствия:** система работает в любом окружении; источник решения виден в трассировке (`trace.source`).

### ADR-011. Ответ робота — из фраз набора, без второго вызова модели

- **Статус:** принято, реализовано в #24.
- **Контекст:** ТЗ ценит задержку и запрещает выдумывать факты; набор содержит начальные фразы сценариев на ru и kk и
  шаблон уточняющего вопроса.
- **Решение:** ответ собирается из `responses` сценариев и `response` системных намерений на языке клиента.
- **Последствия:** одна модель на ход вместо двух — меньше задержка; робот говорит только то, что есть в данных.

### ADR-012. Журнал ходов в PostgreSQL для супервизора

- **Статус:** принято, реализовано в #26.
- **Контекст:** ТЗ: супервизор видит, какие сценарии выбирались, где робот сомневался и ошибся.
- **Решение:** миграция 001 — `dialogs` и `turns`; выбранный сценарий и уверенность — столбцы для статистики, решение и
  задержка — JSONB для показа; запись после замера задержки и best effort.
- **Последствия:** история ходов переживает перезапуск; сбой базы не обрывает разговор.

### ADR-013. Политика минимального возраста релиза pnpm

- **Статус:** принято, реализовано в #22.
- **Контекст:** pnpm 12 не устанавливает пакеты, опубликованные менее суток назад; свежий Next.js 16.3.6 ломал установку.
- **Решение:** Next.js закреплён на 16.3.5; политика безопасности не ослабляется исключениями.
- **Последствия:** установка по lock-файлу проходит везде; обновление зависимостей — не раньше суток после релиза.

### ADR-014. Интерфейс на трёх языках без внешних библиотек

- **Статус:** принято, реализовано в #27.
- **Решение:** словари `messages/{ru,kk,en}.json`; русский словарь задаёт тип, недостающий ключ ломает сборку; язык
  интерфейса не связан с языком разговора.
- **Последствия:** перевод не отстаёт от интерфейса; ноль новых зависимостей.

### ADR-015. Резервный путь при сбое сервиса выбора сценария

- **Статус:** принято, реализовано в #23; дополняет ADR-010.
- **Контекст:** ADR-010 описывает случай «сервиса нет»: `ROUTER_URL` не задан, решение принимает ядро или демо-режим.
  Случай «`ROUTER_URL` задан, но сервис недоступен или отвечает ошибкой» покрыт не был — ход получал `SYS_UNCLEAR`
  с пометкой «маршрутизатор недоступен», то есть падение одного сервиса превращало каждую реплику в уточнение.
- **Решение:** при сбое сервиса (сеть, ответ 5xx, таймаут) `apps/web/app/api/turn/route.ts` выбирает сценарий
  маршрутизатором ядра (`OPENAI_API_KEY` задан) или демо-режимом (ключа нет). Причина сбоя пишется в `trace.error` и
  в журнал ходов, `source` — `core-llm` или `demo`. Если сервис не отвечает (имя не разрешилось, соединение отклонено,
  истёк таймаут HTTP-запроса), он 30 с не опрашивается: остановленный контейнер не отказывает сразу — имя `router` в сети
  Compose не разрешается ~5 с, и без паузы каждый ход ждал бы их. Если сервис ответил HTTP-ошибкой (502, 503, 504) или
  ответом вне контракта, он жив: этот ход идёт резервным путём, следующий — снова в сервис. Первая версия включала паузу
  после любого сбоя; в замере лида на dev-наборе (ревью PR #30) один ответ 504 (модель не уложилась в 6 с) увёл следующие 22 реплики на
  резервный путь, где пришлись все 4 промаха full_match. Логика — `apps/web/lib/server/router-service.ts`, тесты рядом.
- **Последствия:** разговор не обрывается из-за падения сервиса. Первый ход после сбоя медленнее (8044 мс в замере:
  ~5 с на разрешение имени, затем ядро), следующие в паузе идут резервным путём без опроса сервиса (1574 мс).
  Замер точности на dev-наборе есть только для сервиса (`docs/ROUTER_LOG.md`), для резервного пути — нет; какой путь
  принял решение, супервизор видит по `source` в трассировке и журнале. Проверено `docker compose stop router`: ход
  получил `source = core-llm` и `error = fetch failed`, повтор в паузе — `source = core-llm` без обращения к сервису,
  оба хода записаны в журнал.

### ADR-016. Режим звонка: серверное распознавание ru и kk, голос сервера, перебивание

- **Статус:** принято, реализовано в #33; уточняет ADR-009.
- **Контекст:** ТЗ: «жюри говорит в микрофон — робот распознаёт и отвечает голосом»; из 10 проверочных реплик две на
  казахском и одна со смешением языков. Распознавание браузера слушает один заранее выбранный язык и режет смешанную
  фразу; голоса для казахского в Windows часто нет, и ответ читается русским голосом. Замер словаря терминов (#25):
  WER казахского 0.46 без подсказки и 0.05 с подсказкой, смешанной речи 0.21 и 0.00.
- **Решение:** при наличии ключа интерфейс предлагает звонок. Браузер держит микрофон открытым весь звонок и
  определяет конец фразы по тишине с порогом от измеренного шума; запись уходит в `POST /api/stt` (`gpt-transcribe`,
  `languages: ["ru","kk"]`, подсказка из словаря терминов набора); ответ робота звучит из `GET /api/tts`
  (`gpt-4o-mini-tts`, потоком). Во время ответа запись продолжается: речь клиента поверх робота останавливает голос
  сразу, а начало фразы уже записано. Сценарий по-прежнему выбирает LLM-слой на сервере — меняется канал, а не то,
  кто принимает решение. Потоковую голосовую модель (speech-to-speech) не выбрали: в ней выбор сценария скрыт внутри
  модели, а ТЗ требует видимого выбора с обоснованием и ответов только по данным набора.
- **Последствия:** казахская и смешанная речь распознаются дословно (проверка по кругу: 0,85–1,5 с). Задержка от конца
  речи до первого звука — 3–4 с (0,8 с тишины, распознавание ~1 с, выбор сценария ~1,6 с, первый звук синтеза
  ~0,7 с) против ориентира 1,5 с; путь к сокращению — потоковое распознавание и быстрый путь (#11). Без ключа
  остаются распознавание и синтез браузера (Положение §5.6.6).

### ADR-017. Статистика журнала для супервизора считается в базе

- **Статус:** принято, реализовано в #36.
- **Контекст:** ТЗ: супервизор видит, какие сценарии выбирались, где робот сомневался и ошибся. Журнал ходов растёт с
  каждым разговором; выгружать его строки в приложение, чтобы посчитать доли, — лишняя нагрузка и память.
- **Решение:** `GET /api/stats` — три агрегатных запроса PostgreSQL по окну 24 часа на индексе `created_at`: доли
  действий, сбои источника, задержка p50/p95 (`percentile_cont`), частые сценарии, последние сомнительные ходы
  (уточнение, оператор, уверенность ниже порога запуска 0.75, ошибка). Числа из pg приводятся к числам в чистой
  функции с тестами. Интерфейс обновляет блок после каждого хода и по кнопке, без периодического опроса.
- **Последствия:** сводка не зависит от размера журнала в памяти приложения; окно и пороги — именованные константы
  в `apps/web/lib/server/stats.ts`.
