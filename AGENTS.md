# AGENTS.md — правила работы над проектом

Читать перед любым коммитом. Относится к людям и к AI-инструментам, которые помогают команде.

Репозиторий команды IITU+SPARTANS на хакатоне HackAlem AI 2026. Трек 09 «Коммуникации»,
кейс «Voice Router — гибридный голосовой AI-робот с LLM-слоем выбора сценария», владелец задачи Halyk Bank.
Проекты проверяет AI-скоринг и эксперты; история коммитов проверяется.

## Условия, нарушение которых снимает участие

Источники: Положение хакатона (редакция 22.09.2026) и «Правила зачёта участия».

- **Промежуточный результат за каждый час** (§5.4.8): изменения в коде или репозитории, функционал,
  схема архитектуры, тесты, подготовленные данные. Коммитить по ходу работы, естественно и часто;
  ни один час не должен остаться без результата.
- **Только этот репозиторий** (§5.4.9, §5.4.11): основная разработка ведётся здесь, история разработки
  подтверждаема. Не переносить готовый код одним коммитом.
- **Личный вклад каждого участника**: каждый коммитит своим аккаунтом.
- **Готовый продукт или чужой код без раскрытия не допускаются** (§5.4.5, §5.4.6). Использованные
  инструменты, библиотеки, модели и данные перечислены в README, раздел «Инструменты и источники» (§5.4.4).
- **Запуск по README** (§5.4.16): если итоговую версию не удаётся запустить по инструкциям в репозитории,
  команда не допускается к дальнейшему отбору.
- **Итоговая версия — состояние репозитория в 18:00** (§5.4.13). К 17:45 проект должен запускаться;
  последний час — стабилизация, не новые функции.

## Требования кейса (ТЗ Halyk Bank)

- Выбор сценария — на LLM-слое. Intent-классификатор энкодерного типа не засчитывается.
- Голос в вебе: жюри говорит в микрофон, робот отвечает голосом. Текст — резервный канал.
- Панель трассировки после каждой реплики: сценарий, обоснование, альтернативы, время по этапам.
- Русский и казахский, включая смешение языков внутри фразы.
- Необратимые действия — только после явного подтверждения клиента; где робот не справляется — передача
  оператору с контекстом.
- Запуск одной командой. Хардкод сопоставления проверочных реплик со сценариями запрещён.

Критерии из ТЗ: соответствие задаче и работоспособность 25 · техническая реализация 25 ·
README и воспроизводимость 25 · ценность и применимость 15 · потенциал и оригинальность 10.

Развёртывание на внешнем сервере не обязательно; обязательна воспроизводимость: запуск одной командой
по README (ТЗ, раздел 10; ответы организаторов на Q&A 22.09.2026).

## Как ведём разработку

1. **TDD.** Каждый модуль начинается с падающего теста; затем реализация до зелёного; затем рефакторинг.
2. **Модульный монолит.** Модули с явными границами и контрактами (Zod). Состояние — в PostgreSQL.
3. **Миграции.** Схема БД меняется только нумерованными SQL-миграциями в `db/migrations/`, каждая с
   комментарием о назначении.
4. **Каждое утверждение README соответствует коду** на момент коммита. Незавершённое помечено как план.
5. **Секреты** — только в `.env`, который исключён из репозитория. Ключи и токены не попадают в код,
   коммиты, issues и чаты.

## Коммиты

- Автор коммита — участник команды, своим аккаунтом. Служебные подписи сторонних инструментов в
  сообщениях коммитов не используются; AI-инструменты раскрыты в README.
- Сообщение: тип и область, затем что сделано и зачем (`feat(router): …`, `test(policy): …`, `docs: …`).
  Один язык, без эмодзи.
- Перед отправкой — `git pull --rebase`, чтобы не перетирать работу коллег.
- Историю не переписывать: без `push --force`, без правки уже отправленных коммитов.
